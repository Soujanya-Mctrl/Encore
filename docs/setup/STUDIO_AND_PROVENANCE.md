# Artist Studio and provenance integration

The Expo client uses the existing Encore session. Expo native sends its bearer token. Expo web sends its same-origin session cookie. The typed calls in `apps/mobile/src/lib/encore-studio.ts` are ready for the Studio screens.

| Action | Request or behavior |
| --- | --- |
| Enable Studio | `POST /api/v1/studio/enable` with the artist's display name and optional profile preferences. The same account keeps its listener role. Repeated enable calls return the existing channel. |
| List or open drafts | `GET /api/v1/studio/tracks` and `GET /api/v1/studio/tracks/:id`. The owner receives private revision history and a stable track ID. |
| Stage an MP3 | `POST /api/v1/uploads/init` with the byte size. PUT the exact audio to the returned signed URL with `Content-Type: audio/mpeg`. Keep the Encore bearer token on Encore requests. |
| Create the draft | `POST /api/v1/uploads/finalize` with the grant and release metadata. The server checks the byte count, parses the MP3 frames, and digests the bytes. The grant expires after 10 minutes. Retrying the same finalize returns the existing track. |
| Edit metadata and credits | `PATCH /api/v1/studio/tracks/:id` with `{ expectedVersion, metadata }`. Edits reset the verification outcome and create a hash-linked revision. On 409, reload before saving. |
| Verify evidence | GET then POST `/api/v1/studio/tracks/:id/provenance`. Use the returned revision and binding. The response is a new draft revision. Identical concurrent submissions return the same result. |
| Submit | `POST /api/v1/tracks/:id/submit` with `{ expectedVersion }`. This freezes the current draft for review. Separate reviewer approval and finalized registry anchoring remain part of publication. |
| Publish or delist | The existing `/api/v1/tracks/:id/anchor` flow prepares, accepts and confirms the creator's signed registry transaction. `POST /api/v1/studio/tracks/:id/delist` with the current version removes the release and previews from Encore's public catalog. Existing preview URLs expire on their original schedule. |

Apply `202611280012_studio_release_actions.sql` after the catalog and onboarding migrations. The existing owner-only catalog model is used for this slice. The API creates the first draft when the audio is finalized. Editor access, provider-specific credential issuance, and replacing a published version are later extensions.

## Verification modes

Set `ENCORE_PROVENANCE_DEMO=true` for demo fixtures. The optional `demoScenario` is `supported`, `missing`, or `ai_signal`. Demo results are visibly simulated on the Passport and keep the track's evidence status unverified.

Set `ENCORE_PROVENANCE_DEMO=false` for real verification. Configure distinct trusted BIP340 public keys in `ENCORE_PROVENANCE_PROVIDER_KEY` and `ENCORE_PROVENANCE_EXPORTER_KEY`. Rotate or remove keys through server configuration. Its issuer-set digest is part of each proof binding. Historical Passport versions preserve the key-set digest used at verification. A proof submission with no configured trust returns 503. No evidence yields an unverified result.

The implemented real policy supports a single scoped finding, **a trusted provider generated the instrumental and a trusted exporter bound it to this release**. The provider signs a domain-separated canonical contribution record. The exporter signs the contribution digest, graph commitment, and exact audio SHA-256. The credential holder proves knowledge of the credential's fresh private scalar with a BIP340 Schnorr proof bound to both signed statements. The server verifies the two issuer signatures and proof of possession. The exporter remains responsible for checking graph linkage. This slice does not run a general-purpose ZK circuit over a hidden production graph.

Real issuer and exporter integrations must issue the two signatures over the digests returned by `provenanceMessages`. The digest input binds track ID, target Passport version, audio hash, policy version, role and issuer-set hash. The supported operation is `generate` for the `instrumental` role. Use a per-credential public key with no stable artist or account identifier. Graph commitments should be generated by the trusted exporter with a private random salt.

The local prover accepts a private JSON file containing `binding`, `graphHash`, `contributionSignature`, `exportSignature` and the 32-byte hex `credentialSecret`.

```sh
node --import tsx packages/infrastructure/src/provenance/prove-local.ts /private/path/credential.json
```

Send only the resulting proof object and `expectedVersion`. Encore stores the outcome, policy, graph and issuer-set commitments, and a submission digest inside the immutable Passport. Witnesses, signatures, and the per-credential key stay out of the saved and public Passport. Never place private credential files in the workspace or use the public test issuers in a deployed environment.

MP3 tags are treated as advisory. An explicit AI-related tag on a human-created claim records an unverified outcome. A clean tag or an artist-supplied credit by itself supplies no evidence of human creation. The handoff reserves full-track corroboration for tools with sufficient coverage. An instrumental finding therefore leaves the overall declaration unverified and keeps rights and moderation independent.

## Verification

```sh
pnpm test
pnpm typecheck
psql "$LOCAL_DATABASE_URL" -f supabase/tests/studio_release_actions.sql
ENCORE_RUN_STUDIO_E2E=1 pnpm test:e2e tests/e2e/studio
```

Use a disposable database and private storage for the browser test. Run once per mode. The real-mode test uses `fixtureIssuers` in `packages/infrastructure/src/provenance/fixture.test-helper.ts`, which are public test keys. Use the [BIP340 specification](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki) and [Schnorr proof background](https://www.rfc-editor.org/rfc/rfc8235.html) for the proof primitive.
